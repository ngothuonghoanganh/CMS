# Page Refactor Summary

## Old architecture

The repository already had a `PageService`/`PageController` and a versioned
`PagePayload` document tree, but contracts, persistence model imports, CMS copy,
tests and documentation still used the `LandingPage` concept. The Mongo model
was declared in `landing-page.schema.ts` and persisted to the `landingPages`
collection. Related versions, SEO, forms, analytics and custom domains refer to
the page through the existing `landingPageId` field.

This checkout does not contain a Strapi dynamic zone or `Vision`/
`TextImageContent` component model. The supported content model is the ordered
`PagePayload` tree (`root` → `section`/`container` → content nodes), which is
already suitable for multiple ordered sections.

## New architecture

```text
Workspace / Company
└── Site
    ├── Page
    │   ├── General: title-compatible name, slug alias, description, status
    │   ├── SEO: existing per-page SEO settings
    │   └── Content: ordered versioned PagePayload sections
    ├── Navigation
    └── Domains
```

`Page` is now the canonical business/domain/API/frontend name. The persistence
class is `PageRecord`, the canonical contract is `PageSchema`, and public
responses use `PublicPageSchema`.

## Naming changes

- API/domain services, controllers, persistence imports, frontend types and CMS
  labels now prefer `Page`, `PageRecord`, `PageService`, `PageController` and
  `pages`.
- `name` remains the wire-compatible field and is presented as `Title` in the
  general metadata form.
- The legacy `LandingPageSchema`, `LandingPage`, `PublicLandingPageSchema`,
  `PublicLandingPage` exports and `landing-page.schema.ts` module remain as
  deprecated aliases for existing consumers.
- Technical identifiers that are persisted or exchanged externally, including
  `landingPages`, `landingPageId`, `landing_pages`, `maxLandingPages` and the
  preview message type, were intentionally retained.

## CMS changes

- The sidebar, page inventory, analytics, SEO labels, login copy and product
  copy now use `Pages`/`Page`.
- General metadata is ordered as Title, Slug, Description, Path and Status.
  Slug is kept near Title; Path remains available as the canonical route field.
- Description is limited to 500 characters, saved through create/update APIs,
  copied when a page is duplicated and exposed in public page metadata.
- The builder labels its block palette `Page sections` and keeps the existing
  ordered canvas model. Section order is preserved by the immutable payload
  snapshot.
- Large site inventories are constrained to a scrollable list and fetched with
  server pagination (`limit=20`, `offset`, `total`, `hasNextPage`).

## Page layout

The renderer produces Header/navigation, the ordered PagePayload Main content,
and Footer/navigation. It does not hard-code a marketing-section order. Existing
node styles support base/tablet/mobile rules, and renderer content remains
bounded by the existing payload validation and style safety checks.

## Frontend

The renderer consumes `PublicPage`, validates the response with
`PublicPageSchema`, resolves canonical paths through the optional catch-all route,
and dispatches payload nodes through the explicit component registry. Unknown or
invalid nodes render a safe explanatory fallback instead of crashing the whole
page. Existing navigation and form rendering continue to use the page/site
context.

The public route remains compatible with `/:siteSlug`, `/:siteSlug/:path...`,
custom-domain paths, and the existing `/public/sites/:siteSlug/pages/:pageSlug`
API endpoint. No production public URL was renamed.

## API

Page create, list, update, duplicate, publish, unpublish, preview and public
resolution continue to use the existing endpoints. New canonical path handling
is available through the site resolve endpoint while legacy slug lookup delegates
to the same Page resolver. The Page contract includes optional `description`;
old payloads without it still parse unchanged.

## Migration strategy

No collection rename or destructive data migration was performed. `PageRecord`
uses the existing `landingPages` collection, and all related collections retain
their current foreign-key names. Existing records are read safely, with path and
homepage repair handled by the current compatibility logic. A future, separately
planned migration may copy data to a `pages` collection only after verifying
counts, versions, relations, media and published routes.

## Backward compatibility

- Legacy contract/module aliases are retained and marked deprecated.
- Existing Mongo collection and relation names remain unchanged.
- Existing API endpoint shapes and public URL patterns remain available.
- Existing page payload versions and node types are not rewritten.
- `slug` remains accepted as a compatibility alias; `path` is canonical for new
  routing behavior.

## Tests

The Page contract alias/description behavior has a dedicated contract test. The
existing renderer tests cover ordered nodes, responsive rules, invalid payloads,
and unsupported node fallback. Existing CMS/API integration and E2E coverage
continues to exercise create, update, publish, resolve, forms, SEO, domains and
builder flows.

## Known issues

- The persisted collection name and relation identifiers still contain legacy
  terminology by design; they are technical compatibility debt, not the new
  business concept.
- The project has no Strapi `Vision`/`TextImageContent` components to migrate.
- The renderer development script uses Next Webpack because the current Next 16
  Turbopack dev HMR path can panic on the optional catch-all route and cause
  repeated reloads; production builds are unchanged.
